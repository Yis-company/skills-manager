Outcome Add an explicit update action when a remote CLI version differs from the local app. Install the exact running app version from Yis-company/skills-manager, verify it, select it for that host, and reconnect. Correct both desktop update sources to the fork. No implementation begins until this plan is approved.

Verified findings The installed /Applications/skills-manager.app is 1.41.2 and embeds upstream A-and-Brian/skills-manager URLs for both update paths. The checkout is 1.41.0; the screenshot version is not the version to hard-code. - src-tauri/tauri.conf.json:31 configures the upstream latest.json installer endpoint. - src-tauri/src/commands/settings.rs:167 checks the upstream GitHub latest-release API and uses an upstream fallback link. - src/views/settings/AboutSection.tsx:101 invokes the Tauri updater with only an optional proxy override. - origin is Yis-company/skills-manager. .github/workflows/release.yml publishes assets in github.repository, including macOS arm64/x64 and Linux arm64/x64 CLIs. - src-tauri/src/core/remote_session.rs:285 requires exact version equality before normal remote commands can run. - src-tauri/src/core/remote_host.rs:25 resolves an explicit CLI path first; otherwise the desktop-published stamped CLI wins over PATH. - src/context/AppContext.tsx:238 shows the connection-failure toast with Retry. Settings already exposes a reachability/version probe.

Chosen approach and alternatives Recommended: install a separate versioned remote CLI and persist its absolute path in the existing host cli_path field. This reuses the connection model, needs no database migration, and survives an older remote desktop app republishing its own CLI. The update dialog explains that this connection will use a separate CLI and shows the existing custom path when present. Replacing the desktop-published CLI is smaller initially but can be undone on desktop startup and risks corrupting its version stamp. Updating the whole remote desktop app adds platform installers and permissions beyond this request. Neither alternative is selected.

User experience For a version mismatch, the connection toast offers Review update instead of a futile Retry. Settings offers the same action after its probe reports a mismatch. Other connection failures keep Retry. Open one shared dialog naming the host, current version, required version, and fork source. Explain that it installs the remote connection CLI while retaining the remote desktop app and skill library. The primary button says Update and reconnect; when the remote is newer, use Install matching version and reconnect so a downgrade is explicit. Cancel closes the dialog without changes. Show Checking host, Downloading, Installing, and Reconnecting stages. Disable duplicate actions while pending. Keep failures in the dialog with a retry action and the actual reason. A successful install followed by failed connection is reported as Installed; connection failed. Never display a connected state before the handshake succeeds.

Backend execution Add a small remote installer module and local-only Tauri command. Obtain the host from the local store; derive the target from CARGO_PKG_VERSION. The frontend cannot choose arbitrary release URLs, versions, or remote commands. Add a typed version-mismatch error kind so UI behavior never parses English messages; use the existing probe to obtain version details for the dialog. 1. Reuse SSH target, shell quoting, batch authentication, connect timeout, and keepalive conventions. Probe uname and the absolute home directory using SSH without starting the incompatible CLI. Accept Darwin/Linux on x86_64/arm64 only; unsupported systems fail before installation. 2. Fetch the exact v<app-version> standalone CLI asset over HTTPS from Yis-company/skills-manager using the local HTTP client and local proxy settings. Do not fetch latest, fall back to upstream, forward local credentials, or require remote internet access. Missing/private/unpublished assets produce an actionable error without changing the current CLI selection. 3. Stream the downloaded file over SSH stdin into a uniquely created staging directory under the remote user's ~/.skills-manager/remote-cli/. Keep program text and binary input separate. Use restrictive permissions and quote paths. Bound downloads, output, and subprocess duration; terminate and reap only installer-owned child processes on failure. 4. Run the staged binary with --version; require the expected CLI identity and exact version. Place it in a version-specific directory, using same-filesystem atomic rename. Never overwrite an unrelated file, follow an unexpected destination symlink, alter the desktop-published bridge, or invoke sudo. Clean only temporary paths created by this operation. 5. Handshake against the candidate path to verify the existing protocol and version before changing the local host record. Persist only cli_path, with a check that the host still exists and its SSH target/path did not change during the operation. Preserve host name and other edits. On failure before this step, keep the prior selection. 6. Refresh the host list, disconnect any stale session for this host, and reconnect through the existing switchHost flow. Prevent overlapping update/edit/connect operations; ensure an obsolete async response cannot switch the user back from a newer host selection. No automatic updates, remote desktop replacement, database migration, background cleanup of older version directories, new hashing, or cross-host bulk operations. Existing skill/library paths stay in use. Source authenticity follows HTTPS from the fixed fork release location; --version checks compatibility, not a cryptographic signature.

Desktop update correction Change the Tauri latest.json endpoint and manual GitHub release API/fallback links to Yis-company/skills-manager. Keep intentional upstream attribution links. Reuse a Rust release-repository constant for the manual checker and new CLI downloader; test that it agrees with the Tauri endpoint so these paths cannot silently drift. Preserve existing updater signature verification and its public key. Inspect public release metadata/signature compatibility if available; do not claim signing is proven from endpoint changes alone. No key generation, secret edits, publishing, or installed-app replacement is included. If the fork signs with another key, report the required public-key correction before release.
